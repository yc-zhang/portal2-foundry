# 2026-11-25 实验日志｜从 VMF 到第一间可玩的测试室

今天从一个问题开始：如果让 AI 做一张《传送门 2》工坊地图，它应该生成什么？我们用「拿方块压住按钮，穿过出口」做了第一轮实验。同一个机关足够小，却能同时检验地图编译、实体接线和游戏里的物理交互。

## 先把地图送进游戏

梳理完 Puzzle Maker、Hammer 和工坊的关系后，我们选了 VMF 作为生成目标。第一次用 Valve 的 VBSP 编译时，工具在项目目录里报 `Can't create LogFile`，换到 Windows 临时目录还是一样。把同一份 VMF 放到游戏的 `sdk_content/maps/` 后，VBSP、VVIS、VRAD 依次完成。这个发现后来写进构建脚本：源文件留在仓库，每次在 SDK 下创建独立目录构建，再取回 BSP 和日志。[Windows 构建说明](../docs/portal2-map-build.md)

## 让一句「按钮控制门」变成地图事件

第二个样例把空间、组件和连线写进 JSON。Python 用 srctools 生成墙体和实体，把 `plate.pressed → gate.open` 翻译成 `OnPressed → gate → Open`，也为松开按钮接上关门事件。我们编译了这间小房，并从 BSP 里读回了这两条连线。这次验证的样例叫 `foundry_srctools`；之后反复进游戏修改的是另一张图 `foundry_button`。[样例描述](../chamber.json) · [生成器](../generate_vmf.py)

## 地上的一行字，验证了自定义资源能随图交付

我们把橙色的 `hello rex!` 做成贴花，放在出生点前方的地板上。VMF 引用材质名，VMT 引用 VTF 纹理。构建时用 BSPZIP 把两个文件装入 BSP，再读回资源包、核对游戏目录里的地图副本。后来整间房重做，这行字保留下来，也成了对照光照修复前后效果的标记。[贴花资源](../assets/foundry_button/materials/foundry_button)

## 第一次试玩，编译日志没发现的三个问题都出现了

- **出生时两手空空。** 对照原版入口实例后，我们在出生点放置 `weapon_portalgun`，显式启用蓝、橙两种发射模式。
- **有按钮，找不到方块。** 控制台的 `prop_weighted_cube … has no model name!` 直接指出了缺失项。补上原版 `models/props/metal_box.mdl` 后，方块出现在房间里。
- **按钮附近一片白。** 我们进游戏复现了过曝。即使方块和枪已经可见，白墙的接缝仍几乎消失。对照原版灯具补上距离衰减、重新烘焙后，同一房间的面板纹理、按钮底座和橙字都清晰可辨。[修复前](../media/overexposed.jpg) · [修复后](../media/lighting-fixed.jpg)

按试玩反馈，测试室扩大到 1152 × 768 × 384 个 Hammer 单位，地板和墙换成原版可开传送门的白色面板，按钮嵌入地面。最后一次实机画面里，蓝门和橙门都落在地板上，方块压住按钮，出口已经打开。墙面另外核对了编译后的表面标记。工坊订阅、通关结算与投票留待在线验证。[最终实机截图](../media/portals-and-button.jpg)

## 收工时留下的决定

今天留下了两张地图、生成器、构建脚本、复现说明和分享长图，统一放进仓库的 `POC/`。换电脑后，最快的起点是安装最终版 BSP，在控制台运行 `map foundry_button`。[可玩地图](../foundry_button.bsp) · [当天分享长图](../media/summary.png)

下一轮想验证 LLM 通过 Python / srctools 直接生成 VMF，再交给官方工具编译；Hammer 仅用于检查布局、朝向和 I/O。BEE2 先挑一个带输入或输出的物品做小样，查清它依赖哪些实例、资源和编译规则。等这一步实际跑通，再讨论正式组件库怎么设计。
